1 · Project Overview

TruthGuard AI is a Retrieval-Augmented Generation (RAG) question-answering system built on top of Stripe's official documentation. Unlike a plain RAG chatbot, every answer it produces is automatically audited by a two-layer multi-agent verification pipeline that detects hallucinations, unsupported claims, and contradictions before the answer reaches the user.

The system was designed around a single core problem: language models lie confidently. Even when given accurate source documents, a model can blend facts, invent API parameters, or extrapolate beyond what the context actually says. TruthGuard AI treats this as a first-class concern and quantifies it with an explicit hallucination score (0–100) on every response.

Key Capabilities

  • Answers any question about Stripe payments, billing, webhooks, Connect, and the Stripe API — strictly from crawled Stripe documentation.
  • Runs every answer through a Layer 1 Fact Checker that labels each claim as SUPPORTED, UNSUPPORTED, or CONTRADICTED.
  • Passes those verdicts to a Layer 2 Consistency Guard that assigns a numerical hallucination risk score and a TRUSTED / SUSPICIOUS / HALLUCINATED label.
  • Returns all of this — answer, sources, per-claim verdicts, and the trust score — in a single JSON response rendered in a polished dark-themed chat UI.
Design Principle
The system never trusts its own output. Every answer is treated as a hypothesis to be verified against the source documents it was generated from.

The architecture separates concerns into four layers:

  1. Presentation — FastAPI serves the HTML UI and exposes a single POST /ask endpoint.
  2. Orchestration — LangGraph's StateGraph wires five nodes in a directed acyclic graph, passing a shared typed state object between them.
  3. Intelligence — Three independent Gemini LLM calls (generate, fact-check, consistency-guard) and one embedding call (retrieve) via direct REST.
  4. Storage — Pinecone Serverless holds the 3072-dimensional vector embeddings of all crawled Stripe documentation chunks.

4 · Data Ingestion Pipeline

The ingestion pipeline (ingestion/scrape_stripe.py) is a one-time (or periodic) batch job that populates the Pinecone vector database with Stripe documentation content.

4.1 Web Scraping Strategy

The crawler starts from five seed URLs covering the main Stripe documentation areas:

https://stripe.com/docs/payments
https://stripe.com/docs/api
https://stripe.com/docs/webhooks
https://stripe.com/docs/billing
https://stripe.com/docs/connect

For each page it visits:

  1. Fetches the page with a realistic User-Agent header and a 1-second politeness delay.
  2. Removes all <nav>, <footer>, <script>, <style>, <header>, and <aside> elements — keeping only the main documentation content.
  3. Extracts all <a href> links pointing to stripe.com/docs/* without query parameters or anchors, and adds them to the visit queue.
  4. Respects a hard cap of 100 pages to avoid unbounded crawling.
  5. Tracks visited URLs to prevent duplicates.

4.2 Chunking Algorithm

Raw page text is split into overlapping chunks to preserve context across chunk boundaries:

ParameterValueRationale
Chunk size500 charactersFits comfortably within embedding model's token limit; small enough for precise retrieval
Overlap100 charactersPrevents sentence/concept truncation at boundaries
Min length50 charactersFilters out navigation fragments and empty sections

Chunks are created with a sliding window:

start = 0
while start < len(text):
    end = start + CHUNK_SIZE          # 500
    chunks.append(text[start:end])
    start += CHUNK_SIZE - CHUNK_OVERLAP  # advance by 400

4.3 Embedding and Vector Storage

Each chunk is embedded using the Gemini Embedding model via the embedContent REST endpoint. Each vector is stored in Pinecone with the following metadata:

Metadata FieldContents
urlSource page URL (used as citation in answers)
page_titleHTML <title> of the page
chunk_indexPosition of this chunk within the page
textRaw chunk text (returned alongside search results)

Vector IDs are computed as MD5(url + "||" + chunk_index), making upserts idempotent — re-running the scraper on the same pages overwrites existing vectors without duplication.

Rate Limiting
The Gemini Embedding free tier allows 100 requests per minute. The ingestion script enforces a 0.7-second inter-call delay (≈ 85 calls/min) and retries 429 responses with exponential backoff: 15 s → 30 s → 60 s → 120 s → 240 s → 480 s.

5 · LangGraph Multi-Agent Pipeline

The query pipeline is implemented as a LangGraph StateGraph — a directed graph where nodes are Python functions and edges define the execution order. LangGraph manages state passing, node execution, and graph traversal.

5.1 State Design

All nodes share a single typed state dictionary defined as a TypedDict:

class PipelineState(TypedDict):
    query:              str    # original user question
    context:            str    # retrieved doc chunks as a formatted string
    sources:            list   # [{url, title}] for citation
    answer:             str    # LLM-generated answer
    fact_check_result:  dict   # Layer 1 agent output
    consistency_result: dict   # Layer 2 agent output
    final_output:       dict   # assembled response returned to API

LangGraph passes the full state to each node. Nodes return only the keys they modified (partial updates), which LangGraph merges back into the shared state before calling the next node.

5.3 Node 1 — Retrieve (rag/retriever.py)

Input: query string
Output: context (formatted string), sources (list of URLs)

The retrieval node converts the user's question into a 3072-dimensional vector using the Gemini Embedding REST API with task type RETRIEVAL_QUERY, then queries Pinecone for the top-5 most similar document chunks by cosine similarity.

The resulting chunks are formatted as:

[Source: https://stripe.com/docs/webhooks | Stripe Webhooks]
When a webhook event occurs, Stripe sends an HTTP POST request ...

---

[Source: https://stripe.com/docs/api | Stripe API Reference]
Webhook endpoints must be able to handle POST requests ...

This formatted context string is what gets injected into the LLM prompt in Node 2.

5.4 Node 2 — Generate (rag/generator.py)

Input: context, query
Output: answer string

The generator constructs a two-part prompt:

SYSTEM: You are TruthGuard AI, a precise assistant for Stripe's official
documentation. Answer ONLY from the provided context — never from general
knowledge. If the context is insufficient, say so explicitly. Never
fabricate API endpoints, parameters, or pricing details.

USER:  Context from Stripe documentation:
       {context}

       Question: {query}

       Answer strictly from the context above:

The temperature is set to 0.1 to bias toward factual, deterministic output while allowing some natural language variation.

Strict Grounding Instruction
The system prompt's "never from general knowledge" clause is intentional. Without it, Gemini draws on its training data to fill gaps in the retrieved context — which is precisely the behaviour we want to detect, not encourage.

5.5 Node 3 — Fact Check / Layer 1 Agent (agents/fact_checker.py)

Input: answer, context
Output: fact_check_result dict

This agent receives the generated answer and the source context and is instructed to extract every distinct factual claim from the answer and verify each one independently against the context. It returns structured JSON:

{
  "claims": [
    {
      "claim": "Webhooks must be verified using the Stripe-Signature header",
      "verdict": "SUPPORTED",
      "reason": "Context explicitly states: use the stripe.webhooks.constructEvent method with the Stripe-Signature header."
    },
    {
      "claim": "Stripe sends webhooks within 500 milliseconds",
      "verdict": "UNSUPPORTED",
      "reason": "No timing information found in the retrieved context."
    }
  ],
  "overall_verdict": "FAIL",
  "summary": "One of two claims lacks documentation support. ..."
}

Verdict definitions:

VerdictMeaning
SUPPORTEDClaim is directly and clearly backed by the retrieved context
UNSUPPORTEDClaim is not addressed in the context (may or may not be true in reality)
CONTRADICTEDClaim explicitly contradicts what the context states

overall_verdict is PASS only when every claim is SUPPORTED.

The temperature for this agent is 0 — maximum determinism for consistent verdicts.

5.6 Node 4 — Consistency Guard / Layer 2 Agent (agents/consistency_guard.py)

Input: query, answer, fact_check_result, context
Output: consistency_result dict

The consistency guard performs a second-layer audit. It receives the full Layer 1 output (claim verdicts) plus the original answer and context, and makes a holistic judgement about hallucination risk. It also looks for issues the claim-by-claim approach misses:

  • Internal inconsistencies within the answer itself
  • Answers that technically cite supported facts but mislead through selective framing
  • Scope violations — answering beyond what was asked using fabricated details
  • Overconfident phrasing when context is thin

Output format:

{
  "hallucination_score": 23,
  "label": "SUSPICIOUS",
  "final_summary": "The answer is mostly accurate but includes one timing claim not present in the retrieved documentation. The core explanation of webhook verification is well-supported.",
  "additional_flags": ["unverified_timing_claim"]
}

5.7 Node 5 — Compile (graph/pipeline.py)

Input: all accumulated state fields
Output: final_output dict

The compile node assembles all previous outputs into the final response dictionary that the FastAPI endpoint returns as JSON:

{
  "query":    "How do I verify a Stripe webhook?",
  "answer":   "...",
  "sources":  [{"url": "...", "title": "..."}],
  "fact_check": { "claims": [...], "overall_verdict": "FAIL", "summary": "..." },
  "consistency": { "hallucination_score": 23, "label": "SUSPICIOUS", ... }
}

6 · Hallucination Detection Deep Dive

6.1 Why Two Layers?

A single agent can verify claims in isolation but cannot reason about the overall character of an answer. Two independent passes address different failure modes:

LayerWhat it catchesWhat it misses
Layer 1 — Fact CheckerIndividual claims unsupported or contradicted by the contextSubtle framing issues, selective omission, cumulative overreach
Layer 2 — Consistency GuardHolistic risk assessment, internal inconsistency, scope violations, overconfident toneDetailed per-claim evidence (relies on Layer 1 for that)

The two-agent design is a deliberate tradeoff: Layer 1 provides granular, auditable evidence; Layer 2 provides a summary judgement that integrates both the claim verdicts and its own independent reading of the context.

6.2 Claim Extraction Logic

The Layer 1 agent is instructed to extract atomic factual claims — the smallest unit of verifiable assertion. For example, the answer sentence:

"You can verify webhooks using Stripe's constructEvent method, which checks the Stripe-Signature header and requires your webhook signing secret."

…would be decomposed into three separate claims, each verified independently:

  1. Webhook verification uses constructEvent
  2. constructEvent checks the Stripe-Signature header
  3. constructEvent requires a webhook signing secret

The strictness rule is important: if the context only partially addresses a claim (e.g., mentions constructEvent but not the signing secret), the claim is marked UNSUPPORTED rather than SUPPORTED. This conservatism biases the system toward flagging uncertainty rather than suppressing it.

6.3 Hallucination Score

The Layer 2 agent assigns a score from 0 to 100 based on a holistic reading:

Score RangeLabelInterpretation
0 – 20TRUSTEDAll or nearly all claims supported; answer stays within context scope; appropriate hedging where needed
21 – 50SUSPICIOUSSome unsupported claims; answer may go slightly beyond context; warrants user caution
51 – 100HALLUCINATEDSignificant fabrications, direct contradictions, or answer far exceeds what context supports

The score is informed by but not mechanically derived from the Layer 1 claim counts. The Layer 2 agent also weighs the importance of unsupported claims (a fabricated API endpoint is more dangerous than an unsupported stylistic assertion), internal coherence, and whether the answer appropriately communicates uncertainty.

6.4 JSON Output Parsing

Both agents are prompted to return only a valid JSON object. The parser (_parse_json) applies three-stage recovery:

  1. Strip leading/trailing markdown code fences (```json ... ```) which models sometimes add despite instructions.
  2. Attempt direct json.loads().
  3. On failure, use a regex to extract the first {...} block from the raw output and retry parsing.
  4. On final failure, return a safe default object (FAIL / SUSPICIOUS) with the raw output embedded in the summary field for debugging.

7 · Model Discovery & Resilience

A key operational challenge was that Google's embedding and LLM models have different names available per API key and API version. Rather than hardcoding model names that may not exist, both the embedding and LLM subsystems auto-discover the correct model at startup.

7.1 Embedding Model Discovery

On startup (and on the first embedding call), rag/retriever.py calls GET /v1beta/models and filters for models with "embedContent" in their supportedGenerationMethods. It then selects from a preference list:

_PREFERRED_EMBED = [
    "models/text-embedding-004",           # preferred
    "models/text-multilingual-embedding-002",
    "models/embedding-001",
]

If none of the preferred models are available, it uses the first embedContent-capable model returned by the API (in this deployment: models/gemini-embedding-001 producing 3072-dimensional vectors).

7.2 LLM Model Discovery

The same pattern is applied in rag/llm_client.py for generateContent models:

_PREFERRED_LLM = [
    "models/gemini-2.5-flash",    # best free-tier quality
    "models/gemini-2.0-flash",    # fast, stable fallback
    "models/gemini-2.0-flash-lite",
    "models/gemini-flash-latest",
    "models/gemini-2.5-pro",
]

7.3 503 Overload Fallback

When a model returns HTTP 503 (overloaded), the system does not fail the request. Instead:

  1. The overloaded model is added to a session-scoped _overloaded: set[str].
  2. The active model cache is cleared.
  3. get_llm_model() re-runs and skips any overloaded model, returning the next preference.
  4. The call is retried with the new model (max 4 attempts).
  5. If all models are overloaded, the set is cleared and discovery starts over.

7.4 Rate Limit Handling (429)

Both the embedding scraper and the LLM client handle HTTP 429 with exponential backoff:

  • Embedding (scraper): 15 s → 30 s → 60 s → 120 s → 240 s → 480 s (6 attempts)
  • LLM (call_llm): 30 s → 60 s → 120 s (3 attempts, then error)

7.5 Pinecone Index Dimension Auto-Correction

The embedding dimension (3072 for gemini-embedding-001, 768 for older models) is detected at ingestion time by measuring the actual vector returned from the probe call. If an existing Pinecone index has a different dimension, it is automatically deleted and recreated:

info = pc.describe_index(PINECONE_INDEX_NAME)
if info.dimension != embed_dim:
    pc.delete_index(PINECONE_INDEX_NAME)
    pc.create_index(name=PINECONE_INDEX_NAME, dimension=embed_dim, ...)

9 · Frontend Architecture

The frontend is a single self-contained HTML file (api/templates/index.html) with no external dependencies. It communicates with the FastAPI backend via a single fetch() call to POST /ask.

9.1 Component Structure

  • Header bar — branding, live status pill
  • Chat scroll area — message bubbles, welcome screen with suggestion chips
  • Bot response card — answer bubble + Trust Card
  • Trust Card — badge (TRUSTED/SUSPICIOUS/HALLUCINATED), animated score bar, expandable claims section, expandable sources list
  • Input area — auto-resizing textarea, send button, keyboard shortcut hint

9.2 Trust Score Animation

When a response arrives, the hallucination score animates from 0 to its final value over ~1 second using setInterval, and the score bar fills via a CSS transition: width 1.1s cubic-bezier(). The colour of both the bar and the numeric counter is driven by the label field: green for TRUSTED, amber for SUSPICIOUS, red for HALLUCINATED.

9.3 Typing Indicator

While awaiting the pipeline response (which takes 5–15 seconds due to three sequential LLM calls), the UI shows a three-dot bouncing animation inserted as a DOM node, then removed when the response arrives. This prevents the user from perceiving the system as frozen during LLM inference.

10 · Setup & Deployment Guide

Prerequisites

  • Python 3.12 or higher
  • Gemini API key from aistudio.google.com/app/apikey (free)
  • Pinecone API key from app.pinecone.io (free Serverless tier)

Installation

git clone <repo>
cd truthguard
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt

Configuration

cp .env.example .env
# Edit .env and set:
GEMINI_API_KEY=your_key_here
PINECONE_API_KEY=your_key_here
PINECONE_INDEX_NAME=truthguard

Step 1 — Run Ingestion

python3 ingestion/scrape_stripe.py

Expected output:

Probing embedding models...
  Embedding model (auto-detected): models/gemini-embedding-001
  Dimension: 3072  OK
[1/100] Scraping https://stripe.com/docs/payments
  Upserted 18 chunks (total: 18)
...
Ingestion complete. Pages: 100, Vectors: 1843

Re-runnable safely — vectors are upserted (not duplicated) by stable hash ID. Run multiple times to build up coverage without hitting the 100-page per-run cap.

Step 2 — Start the Server

uvicorn api.main:app --port 8000

Startup output confirms models:

  Embedding model: models/gemini-embedding-001
  LLM model:       models/gemini-2.5-flash
INFO:     Application startup complete.

Open http://localhost:8000 in your browser.

Important: Do not use --reload
On macOS, uvicorn's --reload flag spawns a subprocess that can fail DNS resolution for external APIs. Use uvicorn api.main:app --port 8000 without --reload in production. For development, always activate the virtual environment with source venv/bin/activate before running any command.
